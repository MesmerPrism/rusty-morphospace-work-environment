# Rusty Morphospace Project Workflow

Use this reference for ordinary project composition, activation, isolated
source work, lifecycle, validation, and instruction impact. Detailed recovery
and audit procedures remain in the resolved work-environment runbooks.
Here, `<work-environment>` is the locator's `work_environment_root`; read its
named runbooks under `<work-environment>/docs/`.

## Resume and scope

Read the nearest project instructions, then its `morphospace/project.spec.json`,
`feature.lock.json`, `workspace.state.json`, current unit when present, and only
the compact-state-named event tail and receipts. Check Git status for every
repository in scope.

The project spec owns composition. The feature lock owns the permitted
feature/effect closure. Workspace state is a resume projection; it does not
replace immutable unit, event, or receipt evidence. Work only inside the
intersection of project and current-unit repositories and paths. Preserve
dirty, detached, divergent, blocked, interrupted, and historical state.

For ordinary continuation, use
`<work-environment>/docs/CURRENT_WORK_VALIDATION.md`: preserve
the authenticated current suffix and explicit prerequisites, and do not retrofit
new proof versions or instruction policy onto retired units. An unchanged
adopted consumer uses `-CurrentWorkOnly -SkipOwnerSelfTests`. Historical audits
and owner self-tests are separate choices.

## Composition and source identity

Resolve owner-issued descriptors into an exact fingerprinted lock. Descriptor
locations are resolver inputs, while lock references are portable,
project-spec-relative forward-slash paths. Reject absolute, parent-traversing,
and out-of-project references. Unlisted, denied, stale, or merely selected
features are inert; runtime activation also needs the selected lock and a
descriptor-approved input with consuming effective evidence.

Keep optional families disabled by default. A downstream adoption names its
baseline shell, disabled neighboring options, and an unrelated absent/inert
feature. Reusable extraction needs an independent consumer or neutral
conformance harness.

Bind cross-repository work to clean exact commits and trees in a source-
composition lock. Keep observed, claimed, validated, and accepted revisions
distinct; prefer clean detached materializations when live checkouts move.
Separate source, build, run, package, client, marker, property, staging, and
other mutable identities. Local coordination claims do not activate a feature
or authorize Git or device work.

For published or deliberately dirty embedded planning authority, use only
`<work-environment>/docs/EXTERNAL_PLANNING_AND_HISTORICAL_RECONSTRUCTION.md`
or
`<work-environment>/docs/UNPUBLISHED_PLANNING_AUTHORITY_MATERIALIZATION.md`.
They preserve source bytes and do not grant Git, validation, acceptance, or
publication authority.

## Lifecycle and validation

Allow at most one current active or validating unit. Inspection and planning
are non-mutating; use owner actions instead of editing state or events. Derive
repository, path, graph, and validation scope from the unit. Keep proposals,
claims, validation, acceptance, publication planning, execution, and device
evidence separate. A pass is evidence, not acceptance; a prepared publication
plan is not execution evidence.

Select `guard_profile` independently from `risk_tier`: `fast` for bounded
product work, `labs` for composition or authority work, and `locked` for
release or workflow trust-root work. Risk tier changes evidence depth only.
For an in-scope failed attempt use `ReturnToActive` and retain its receipt;
use a blocker and `Resume` when work or authority actually stops. A validation-
only unit cannot become product implementation.

Before Claim, use the exact consumer inventory through `Inspect`. Its advisory
result is diagnostic and cannot replace `ready_to_claim` or an explicit guard.
For expensive execution, consume a hash-bound project-produced preflight
observation. It verifies declared non-sensitive assertions and does not produce
build, bridge, or device work.

Select focused or Quick checks while iterating, Standard for coherent handoff,
and Deep only for the declared broad authority or release risk. Freeze the
coherent candidate before its final risk-selected aggregate. Route validation
trust-root changes to
`<work-environment>/docs/EXTERNAL_VALIDATION_AUTHORITY.md` and affected
selection to `<work-environment>/docs/AFFECTED_VALIDATION.md`.
Static admission, dynamic validation, acceptance, and publication remain
separate authorities.

## Boundaries and instruction impact

One owner controls each runtime parameter and state transition. Adapter
readback proves transport; acceptance requires consuming-owner effective
readback. Keep control surfaces separate from high-rate media, pose, depth,
mesh, camera, particle, and GPU-buffer data. Keep UI, CLI, platform, and device
adapters outside reusable authority owners.

Keep portable outputs free of machine paths, private repository and package
identities, credentials, pairing data, raw captures, logs, and private payload
semantics. Preserve owner evidence byte-for-byte; a public wrapper binds only a
sanitized summary and the owner schema/hash.

For authority, module-layout, activation, validation, device-policy,
repository-routing, or public/private changes, follow
`<work-environment>/docs/INSTRUCTION_SYNCHRONIZATION.md`.
Update only the declared affected instructions, README/router, and skills;
never hand-edit a unit to mark its instruction surfaces complete.

## Explicit recovery and historical work

Do not turn an ordinary continuation into an audit or repair. Use these
runbooks only when the request explicitly selects their named condition:

- `<work-environment>/docs/HISTORICAL_UNIT_ADOPTION.md` for terminal legacy
  vocabulary and in-flight compatibility projections.
- `<work-environment>/docs/HISTORICAL_SUPERSESSION_COMPATIBILITY.md` for its
  one authenticated idle-history shape.
- `<work-environment>/docs/EXTERNAL_PLANNING_AND_HISTORICAL_RECONSTRUCTION.md`
  for published projections and reconstructions.
- `<work-environment>/docs/AUTONOMOUS_ITERATION.md` for typed
  lifecycle corrections, blocked recovery, active-scope amendments, selectors,
  interruption, and publication-preparation procedures.

Each route preserves historical bytes and has its own preconditions. None is a
general status edit, chronology repair, Git mutation, validation, acceptance,
publication, or device authority.
